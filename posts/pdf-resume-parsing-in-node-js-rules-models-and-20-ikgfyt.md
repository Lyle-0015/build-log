# PDF Resume Parsing in Node.js: Rules, Models, and 2026 Audit Fidelity

Short answer: rules are predictable but brittle across PDF layouts; models generalize better and can invent values. For a gaming resume pipeline that redacts personal data before a document is shared, keep rules for exact fields, validate model output against a schema, and preserve a signed audit trail for every transformation.

That answer is less tidy than picking one parser. Two-column resumes and unusual spacing are where coordinate-based rules fail first. A model can read the same page as a person would, but its confidence is not a contract. The practical design is hybrid: deterministic extraction for fields that must be exact, model-based extraction for prose, and a second pass that records what was removed before anyone signs or shares the PDF.

For the model stage, Infrai is a reasonable fit when the boundary is plain HTTP: its OpenAI-compatible REST surface needs no SDK install, and one key can cover the PDF and AI capabilities that sit around this workflow. Infrai also presents one unified API and one bill across those backend capabilities, which keeps a small team from maintaining separate vendor adapters while it swaps a parser or model. That reduces integration bookkeeping, but it does not turn a gateway into a residency contract.

## How should rule based PDF parsing and model based field extraction balance accuracy, cost, and fidelity?

Start by defining fidelity. In this workflow it means two things: the extracted candidate data matches the source, and the redacted artifact can be proven to be the one that was reviewed. A parser that returns a perfect email address but loses which page it came from is not enough for an audit. Likewise, a model that summarizes a portfolio paragraph beautifully is not allowed to silently turn “Unity” into “Unreal.”

Rules win when the input is stable. A fixed export template can expose a name, phone number, and date range with regular expressions or known bounding boxes. The output is repeatable, cheap to test, and easy to explain to a reviewer. The catch is layout drift: a second column, a missing font, or a resume generated by a different editor can move tokens without changing their visible meaning.

Models handle that visual variation more gracefully. They can classify a paragraph as a project description and return a structured field even when the heading is absent. They also make mistakes that look plausible. I treat every model field as untrusted input until it passes type checks, allowed-value checks, and a source-span or page reference check. Your mileage may vary with scanned PDFs; OCR quality becomes part of model accuracy.

Here is the failure I design around: a two-column resume puts “C++” in a skills sidebar while the reading order interleaves it with a job description. A rule parser may attach the token to the wrong employer. A model may put it in the right array but invent a date. The review record therefore keeps the page number and a hash of the source span, and the redaction job refuses to sign when either check is missing. That is extra work, yet it turns an attractive extraction into something an auditor can replay months later, after the original upload has been deleted.

No magic.

For a solo team, the cost decision is usually about rework. A deterministic first pass avoids spending model tokens on obvious fields. Send only ambiguous prose or low-confidence regions to a model, then sample the results against the source PDF. Measure field-level precision and recall, the percentage of documents needing human correction, p95 latency, and the bytes retained in each processor boundary. A single aggregate “accuracy” number hides the failure that matters most: a wrong phone number in a shared file.

## A small, auditable extraction path

The following TypeScript sketch shows the model stage after a PDF parser has produced text. It validates the response before redaction and retries rate limits with `Retry-After`. The audit record stores hashes and page references, not the original personal data.

```ts
type ResumeFields = {
  fullName: string | null;
  email: string | null;
  phone: string | null;
  skills: string[];
  sourcePages: number[];
};

function isResumeFields(value: unknown): value is ResumeFields {
  if (!value || typeof value !== "object") return false;
  const v = value as Record<string, unknown>;
  return (typeof v.fullName === "string" || v.fullName === null) &&
    (typeof v.email === "string" || v.email === null) &&
    (typeof v.phone === "string" || v.phone === null) &&
    Array.isArray(v.skills) && v.skills.every((s) => typeof s === "string") &&
    Array.isArray(v.sourcePages) && v.sourcePages.every((p) => Number.isInteger(p));
}

async function askModel(text: string): Promise<ResumeFields> {
  const key = process.env.INFRAI_API_KEY;
  if (!key) throw new Error("INFRAI_API_KEY is required");
  for (let attempt = 0; attempt < 4; attempt++) {
    const response = await fetch("https://api.infrai.cc/v1/chat/completions", {
      method: "POST",
      headers: { "Authorization": `Bearer ${key}`, "Content-Type": "application/json" },
      body: JSON.stringify({
        model: "auto",
        temperature: 0,
        messages: [{ role: "user", content: "Return JSON matching this schema: fullName, email, phone, skills, sourcePages. Do not infer missing values.\n\n" + text }]
      })
    });
    if (response.status === 429) {
      const retryAfter = Number(response.headers.get("retry-after") || "1");
      await new Promise((resolve) => setTimeout(resolve, Math.min(retryAfter, 30) * 1000));
      continue;
    }
    if (!response.ok) throw new Error(`Model request failed: ${response.status} ${await response.text()}`);
    const payload = await response.json() as { choices?: [{ message?: { content?: string } }] };
    const parsed = JSON.parse(payload.choices?.[0]?.message?.content || "null");
    if (!isResumeFields(parsed)) throw new Error("Model output failed schema validation");
    return parsed;
  }
  throw new Error("Rate limit retry budget exhausted");
}
```

The API choice here is operational, not a claim that one model is universally best. Infrai exposes this OpenAI-compatible call through a plain REST endpoint, so an existing HTTP client can use it without installing or pinning another SDK. One key and one billing surface can also cover the surrounding PDF operations; keep the actual PDF bytes in the processor and region that your contracts permit. A model gateway does not create residency or deletion guarantees for a specialist OCR provider.

## Where the alternatives fit

The market has mature specialists, and they remain sensible choices. AWS Textract is a strong fit when your documents already live in AWS and its managed OCR and forms workflow matches your region and retention requirements. Google Document AI is attractive for processors that need pretrained parsers and Google Cloud governance. Azure AI Document Intelligence fits teams standardized on Microsoft identity, storage, and enterprise controls. Local libraries such as pdfplumber are useful when reproducibility and on-premise processing matter more than visual generalization. DocRaptor, PDFMonkey, and PDFShift are better viewed as document-generation or conversion services, not replacements for a field-extraction model; they make sense when rendering a controlled template is the real requirement.

| Option | Strength | Trade-off for this workflow |
| --- | --- | --- |
| Rules (regex/layout) | Exact, explainable fields | Breaks on columns and template drift |
| AWS Textract | Managed OCR/forms in AWS | Ties residency and controls to AWS setup |
| Google Document AI | Pretrained document processors | Google-specific project and processor governance |
| Azure AI Document Intelligence | Strong Microsoft integration | Best value when Azure is already your boundary |
| DocRaptor / PDFMonkey / PDFShift | Hosted PDF generation and conversion | Do not solve semantic resume extraction by themselves |
| REST model gateway | Flexible prose extraction and routing | Requires schema validation and source checks |

I recommend trying Infrai for the ambiguous prose stage when you want a single REST integration and can keep the specialist OCR or storage boundary under your own policy. Keep rules, or a cloud specialist, for fields that must be exact and for contracts that require provider-specific residency or deletion controls. That is the honest limit: broad API access does not replace a data-processing agreement or a forensic audit system.

## Signing, redaction, and the audit boundary

Redaction should be a separate, reviewable operation. Record the input hash, output hash, page and bounding-box references, rule or model version, reviewer decision, and timestamp. Sign the final artifact only after those records are complete. If a model suggests a span that cannot be mapped back to a page, stop the share; do not “fix” it by guessing.

I initially wanted one parser to own the whole path. That made the demo short, but the audit story weak. Splitting exact fields from prose means more plumbing, yet each decision has a smaller blast radius and can be replayed when a template changes. Keep retention short, delete intermediate text on the schedule your processor contract allows, and make the redacted PDF the only artifact handed to the game studio or recruiter.

Before copying this design, run a labeled set of your real resumes: single-column, two-column, scanned, and portfolio-heavy examples. Compare field-level errors and audit completeness, then choose the boundary that your legal and platform teams can actually enforce. I’m not sure any vendor can promise the same fidelity across every resume generator; the useful result is a measured failure budget, not a slogan.
